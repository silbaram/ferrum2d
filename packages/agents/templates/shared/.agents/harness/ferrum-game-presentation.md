# Ferrum2D 게임 화면 설계와 플레이 검수

이 문서는 consumer 게임의 공통 화면 설계·검수 기준이다. Codex, Claude, Gemini는 이 기준을 참조하고 도구별 사본을 만들지 않는다. 엔진 기능의 보장이나 특정 장르·아트 스타일의 강제 규칙은 아니다.

## 적용 단계

- **설치만 요청한 경우**: 엔진 의존성, 개발 도구, AI 지침과 설치 확인까지만 수행한다. 게임 템플릿, `src/`, `public/`, `index.html`, 예제, UI, viewer, replay fixture를 만들거나 개발 서버를 실행하지 않는다. 기존 게임 파일은 삭제하지 않는다. 없는 게임 검증 스크립트를 설치 완료 조건으로 추가하지 않는다.
- **게임 제작·기능 변경을 요청한 경우**: 아래 설계와 해당 변경에 필요한 플레이 검수를 수행한다. 설치 직후 자동으로 게임 제작을 시작하지 않는다.
- 기존 게임의 작은 수정은 관련 화면·동작만 검수한다. 요청과 무관한 전체 화면 재설계를 강제하지 않는다.

## 구현 전에 정할 것

요청과 기존 프로젝트에서 확인할 수 있는 내용으로 짧은 설계 메모를 남긴다. 불명확한 선택은 가정과 이유를 기록하고, 중요한 요구를 판단할 수 없을 때만 사용자에게 묻는다.

1. 장르와 첫 플레이 목표: 무엇을 조작하고 어떤 행동으로 진행하는가?
2. 주요 플레이 공간과 조작 대상: 액션·탐험에서는 플레이 공간을 우선한다. 큰 브랜드 헤더, 소개문, 카드 프레임, 상시 저널을 관성적으로 넣지 않는다.
3. 메인 카메라: 추적/고정/방 단위 등 선택 이유, 초기 시야, 월드 경계, 이동 중 보여줄 주변 정보. 탐험에서 전체 지도를 기본 시야로 쓰면 조작 대상의 가독성과 발견 경험을 만족하는 이유를 적는다. 미니맵·전체 지도 UI와 메인 카메라를 구분한다.
4. HUD와 보조 화면: 진행에 필요한 정보만 상시 표시한다. 인벤토리·저널·설정은 필요할 때 여는 패널을 우선 검토한다. 모달의 입력 차단, 닫기, 포커스 복귀와 일시정지 정책을 정한다. 플레이 공간을 가리는 패널에서 게임 입력을 차단한다면 포인터뿐 아니라 키보드, 이미 눌린 이동 키와 남아 있는 이동 목표도 처리한다.
5. 지원 화면 크기와 입력: 기준 desktop viewport, 좁은 viewport의 재배치·제약, 키보드/포인터/터치 중 지원 범위. 지원하지 않는 입력을 암묵적으로 약속하지 않는다.

보드·카드·경영·퍼즐 게임, 지도 중심 게임, 페이지에 삽입된 게임에서는 보드나 패널 중심 구성이 적합할 수 있다. 장르와 사용자의 의도가 우선이며 전체 화면 canvas, 추적 카메라, 작은 HUD를 일률적으로 강제하지 않는다.

`shell`, `app`, `src/ui/`는 코드 소유권을 설명한다. 랜딩 페이지나 대시보드 같은 화면 구성을 뜻하지 않는다. HTML/CSS HUD도 허용된다. `createFerrumRuntime({ ui: false })`는 엔진 기본 UI overlay를 끄는 설정이며, canvas나 게임 입력을 끄거나 앱 소유 DOM을 제거하지 않는다. 화면 문제를 해결하려고 설정만 바꾸지 말고 실제 DOM/CSS와 카메라 구성을 확인한다.

## 카메라·월드·에셋

- 월드 좌표 단위, 렌더링 논리 해상도, 실제 CSS viewport 크기를 구분한다. 실제 화면에서 캐릭터, 수집물, 조사 대상, 상호작용 문구를 식별할 수 있어야 한다.
- 이동 중 카메라 추적·경계와 주변 월드의 반응을 확인한다. 고정 카메라가 적합한 장르는 그 이유를 기록한다.
- resize/zoom 전후에 화면↔월드 좌표 변환, 포인터 대상, 렌더링, 물리 collider 정렬을 함께 확인한다. 현재 카메라의 이동·확대를 반영하지 않는 고정 포인터 매핑을 사용하지 않는다. CSS로 월드 전체를 변환하는 구현에서는 변환 후 canvas의 실제 bounding rect를 이용한 매핑도 유효할 수 있으므로 실제 클릭 목표로 검증한다.
- 배경, 움직이는 캐릭터, 상호작용 오브젝트, 전경 가림, HUD의 책임을 구분한다. 월드 전체를 한 이미지로 합치기 전에 이동·가림·애니메이션·수집 후 변화·환경 변화가 필요한지 검토한다. 정적 배경 자체는 허용되며 장르와 상호작용에 맞게 선택한다.
- 이동에는 방향/애니메이션 등 시각적 반응, 조사·수집에는 즉시 확인 가능한 문구·상태·사운드 등의 피드백을 제공한다. 색상이나 소리 하나에만 진행 정보를 의존하지 않는다.
- 설치된 버전의 public sprite/animation/physics API를 우선 검토한다. 필요한 기능이 없으면 API 제약과 소비자 측 대안의 범위를 보고한다. 설치된 엔진을 패치하거나 엔진 소유 물리·충돌을 TypeScript로 중복 구현하지 않는다.

## 검수와 증거

**기능 검증**과 **플레이 경험 검수**를 별도로 보고한다. build/smoke/replay 성공은 화면 가독성이나 게임다운 경험의 통과 증거가 아니다. 자동 브라우저 동작 확인도 스크린샷을 실제로 검토한 결과와 구분한다.

기능 검증에는 실행한 명령, 성공/실패, 생략 사유를 기록한다. 없는 명령은 실행한 것으로 쓰지 않으며, replay의 `not-configured`를 통과로 바꾸지 않는다.

플레이 경험은 브라우저에서 짧게 실제 조작하고 다음을 확인한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 첫 화면 | 조작 대상, 시작 방법, 주요 조작을 이해할 수 있는가? |
| 가독성 | 실제 표시 크기에서 캐릭터·목표·상호작용 문구가 식별되는가? |
| 이동과 카메라 | 이동 피드백, 카메라/월드 반응, 경계 동작이 설계와 맞는가? |
| 조사·수집 | 대상에 접근해 실제로 조작했을 때 진행과 피드백이 즉시 보이는가? |
| HUD·보조 패널 | 중요한 공간을 가리지 않는가? 패널 클릭·키보드 조작·이전 이동 목표가 가려진 게임을 의도치 않게 움직이지 않는가? 닫은 뒤 조작이 복구되는가? |
| resize·zoom | 지원 desktop과 좁은 viewport에서 HUD 재배치, 가독성, 포인터 목표와 물리 정렬이 유지되는가? 확대 기능이 없으면 해당 검수는 적용 제외로 기록한다. |

프로젝트의 `tests/playtest/` 또는 합의된 개발 증거 경로에 다음 형식으로 기록한다. 비공개 프로젝트 파일이나 스크린샷은 사용자 승인 없이 외부 서비스에 올리지 않는다.

```text
검수 대상: 버전/커밋 또는 프로젝트 사본 식별자, 브라우저, URL, viewport, 입력 방식
설계: 장르, 목표, 플레이 공간, 카메라 선택 이유, HUD/보조 패널, 지원 화면
기능 검증: 명령별 결과, 실패 원인, 생략 사유
플레이 경험: 검수 항목별 pass / needs-revision / not-reviewed / not-applicable + 이유
증거: 시작·플레이 중·좁은 화면 스크린샷 경로, 실제 입력 순서와 관측 결과
남은 문제: 재현 절차, 영향, 수정 또는 후속 작업
```

브라우저를 실행하지 못했거나 스크린샷/동작을 확인하지 않았다면 `not-reviewed`로 남기고 이유를 쓴다. 단일 사례의 실패를 엔진 전체 결함이나 모든 AI 도구의 재현 결과로 일반화하지 않는다.
